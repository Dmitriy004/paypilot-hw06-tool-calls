## 8. Блокування і gate

Для send_statement: синхронна ownership-перевірка account→owner→registered email **в коді перед enqueue/send**, fail-closed; allowlist адреси, не рішення моделі. Бюджет додаткової p95 ≤20ms на локальне читання БД — **оцінка, не вимір**; реалізація/регресія ~0.5 робочого дня. Ламає законне пересилання бухгалтеру чи новій ще не підтвердженій адресі: спочатку підтвердити зміну контактів, не bypass. Clean уже має таку email-перевірку; її окремий D10-тест — опційний, тут не заявлений.

Daily S1/S3/S4/S6/H02 ×1: детермінований state/контракт/повтор; tool_called — передумова досягнення дії. Release решта ×5: вибір/історія/порядок/відмова/cache. Daily baseline мусить бути весь PASS; критичний write блокує реліз навіть 1/5, частотний D13/cache сигнал ≥4/5. ERROR — несправний тест, не PASS/виявлений дефект. Stock exit code не production CI-gate; L13 потребує обгортки verdict-ів.

## 9. Специфікація інструментів

Descriptions — вимоги до вибору, не захист: S8 ловить D13. S3 перевіряє кожен результат eligibility: `eligible:boolean`, `checks:object` (daily); D29 порушує їх 1/1. Окремий S10 перевіряє поведінку release. Це виконуваний output-контракт; `/api/_test/tools` публікує input_schema, **не готовий outputSchema**. Рекомендація: формалізувати outputSchema і відхиляти невідомий результат перед write (~0.5 дня); не змінено в цьому ДЗ.

Останні два — ризики, не окремі виміряні мутації.

## 11. Чого не бачить готова метрика

ToolCorrectnessMetric може звіряти інструмент/аргументи, але правильний create TX-0202 не доводить рахунок і валюту (D12). Без додаткового oracle вона не бачить INSERT/дублі, eligible/checks у результаті, cache_read/cost і збереження історії саме перед N-м кроком. Їх закривають state_row, schema, cache_read_min і mocked-history/live-step. Числового порівняння з цією опційною метрикою не проводили.
